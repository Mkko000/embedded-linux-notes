💡 الفكرة الكبيرة في سطرين
إنت جاي من عالم الـ PIC والـ AUTOSAR: برنامج واحد (أو شوية tasks متعرّفة وقت الـ compile) شغالين على الـ hardware مباشرة، والـ main() عندك عبارة عن while(1). في Linux الوضع مختلف تماماً: فيه برنامج كبير اسمه الـ kernel قاعد بينك وبين الـ hardware، وكل البرامج التانية (حتى الـ terminal اللي هتكتب فيه) «ضيوف» عنده بيطلبوا منه الخدمة. الوحدة الأولى كلها بيشرح الفكرة دي، وأنا هاخدك أعمق: هنشوف الـ system calls بعينينا، والـ process states، وخريطة الذاكرة، ونحلّ الـ scheduling بالورقة والقلم وبمحاكي تفاعلي.

1.1الـ Bootstrap program — أول كود بيشتغل

الـ RAM لما الكهربا تيجي بتبقى فاضية/عشوائية (volatile)، والـ OS نفسه متخزّن على الـ disk أو الـ SD card. طب مين اللي هيقرا الـ OS من الـ storage ويحطه في الـ RAM؟ لازم يبقى فيه كود صغير موجود في ذاكرة non-volatile والـ CPU يبدأ ينفّذه أوتوماتيك من الـ reset vector. ده الـ bootstrap program (من التعبير «‎pull yourself up by your bootstraps‎» = ترفع نفسك بنفسك)، ومنه جات كلمة boot.

وظايفه بالترتيب: ‎(1)‎ يجهّز الـ hardware الأساسي (clocks، الـ DDR controller، الـ UART عشان يطبع)، ‎(2)‎ يلاقي الـ kernel في الـ storage، ‎(3)‎ ينسخه للـ RAM، ‎(4)‎ يعمل jump لأول instruction فيه ويسلّمه التحكم — ومن بعدها الـ bootloader بيختفي خالص.

🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
في الـ PIC18: بعد الـ reset الـ PC = 0x0000 (الـ reset vector) والـ XC8 حاطط هناك goto للـ startup code (c018.c) اللي بيصفّر الـ .bss وينسخ قيم الـ .data وبعدين ينادي main(). لو عملت bootloader للـ PIC (عشان تحدّث الـ firmware من الـ UART)، هو بيقعد في أول الـ flash وبيعمل goto للـ application. الـ Linux boot هو نفس الفكرة بالظبط بس على مراحل لأن الـ kernel كبير (ميجات) ومحتاج DDR RAM متجهزة الأول.

🤔 ليه الـ boot على مراحل؟
ليه مش مرحلة واحدة زي الـ PIC؟ لأن الـ ROM code صغير ومحدود ومش عارف تفاصيل البورد بتاعتك (نوع الـ DDR وتوقيتاتها)، والـ SRAM الداخلية صغيرة متكفيش الـ U-Boot الكامل. فكل مرحلة بتجهّز «أرض أكبر» للي بعدها: SRAM صغيرة ⇒ DDR كبيرة ⇒ kernel ⇒ user space. وفايدة جانبية: تقدر تغيّر الـ U-Boot والـ kernel من غير ما تلمس الـ ROM.

1.2الـ Operating System — الوسيط

الرسمة المشهورة ظريفة: الـ hardware عنده «Ugly interface» (registers، interrupts، timing، DMA descriptors…) والـ OS بيحوّله لـ «Beautiful interface» (ملفات، processes، sockets). يعني بدل ما برنامجك يكتب في register الـ SD controller عشان يقرا sector، بيقول fopen("notes.txt") وخلاص.

الكلمة المهمة: ‎OS = Kernel‎ + أدوات حواليه. الـ kernel هو القلب اللي شغال في الـ privileged mode؛ الـ shell والـ ls والـ GUI كلها برامج عادية فوقه. «‎Linux‎» بالمعنى الدقيق = الـ kernel بس؛ ‎Ubuntu = kernel Linux‎ + أدوات GNU + برامج = distribution.

🔬 الـ User space والـ Kernel space والـ System calls — نشوفهم بعينينا

الـ CPU الحديث عنده مستويات صلاحية: في ARM اسمها EL0 ‎(user)‎ و EL1 (kernel)، وفي x86 اسمها ring 3 و ring 0. الكود اللي في EL0 ممنوع ينفّذ instructions حساسة أو يلمس ذاكرة الـ kernel أو الـ peripherals؛ لو حاول ⇒ exception ⇒ الـ kernel يقتله (Segmentation fault). طب إزاي برنامجك يطبع على الشاشة؟ بيعمل system call: instruction خاصة (svc #0 في ARM64، syscall في x86-64) بتعمل trap لجوه الـ kernel في مكان محدد، والـ kernel يتأكد من الطلب وينفّذه ويرجع.

حتى printf() في الآخر بتنادي الـ system call write(1, ...). الأداة strace بتورّينا ده:

AUTOSAR OS ‎(OSEK)‎ ده RTOS: كل الـ tasks والـ priorities والـ alarms متعرّفة statically في الـ ‎OIL/ARXML‎ وقت الـ build، والكود كله ‎(OS + tasks)‎ بيتربط في binary واحد شغال في نفس الـ address space (في الغالب privileged، والـ memory protection اختيارية بالـ MPU في الـ Scalability Classes 3/4). Linux عكس ده: البرامج بتتحمّل وتتشال dynamically وقت التشغيل من الـ filesystem، وكل process في address space معزول بالـ MMU، والـ user code عمره ما بيبقى privileged. علشان كده Linux محتاج MMU وذاكرة أكبر بكتير.

1.4Process Management — إزاي 100 برنامج يشتغلوا على 4 cores؟

Program = ملف على الـ disk (مثلاً /usr/bin/ls)، حاجة ميتة. Process = برنامج شغال: ليه PID، ليه ذاكرة خاصة بيه، registers، ملفات مفتوحة، user بيمثّله. Thread = خط تنفيذ جوه الـ process؛ الـ threads اللي في نفس الـ process بيشاركوا نفس الذاكرة (زي الـ tasks في الـ RTOS اللي بيشاركوا الـ globals)، لكن كل thread ليه stack وregisters خاصين بيه. (معلومة: الـ Linux kernel بيعامل الـ process والـ thread تقريباً نفس المعاملة — الاتنين «‎task‎».)

«Each application thinks that it owns the whole system» — ده وهم بيصنعه الـ kernel بحاجتين: ‎(1)‎ الـ virtual memory: كل process شايف address space كامل لوحده، ‎(2)‎ الـ scheduler + الـ context switch: كل كام millisecond الـ timer interrupt يقاطع، والـ kernel يحفظ registers الـ process الحالي ويرجّع registers process تاني — بسرعة لدرجة إن الكل بيبان شغال مع بعض.

Round robin: كل واحد ياخد time slice بالدور (زي طابور). Priority based: الأعلى أولوية ياخد الـ CPU الأول. و «block on events»: لو process مستني data من الـ disk أو ضغطة زرار، مبيضيّعش CPU — بيروح حالة sleeping والـ scheduler يدّي الـ CPU لغيره، ولما الـ interrupt ييجي يصحى.

1.5خوارزميات الـ Real-time scheduling: RM و EDF

الترميز: Ti(P, C) في الرسمة = (Period, execution time). يعني T1(4,1): كل 4 وحدات زمن بييجي job جديد محتاج وحدة CPU واحدة، والـ deadline = بداية الـ period الجاي (implicit deadline). الأسهم لفوق في الرسمة = وصول job (release)، وكل سهم هو كمان deadline الـ job اللي قبله.

الـ Utilization = نسبة الـ CPU المطلوبة: U = Σ C/P = 1/4 + 2/5 + 2/7 = 0.25 + 0.40 + 0.286 = 0.936 ⇒ الـ tasks عايزة 93.6% من الـ CPU.

🟡 متوسط ✍️ مثال: نمشي RM خطوة بخطوة
  1. الأولويات ثابتة حسب الـ period: ‎T1 (P=4)‎ أعلى، بعده ‎T2 (P=5)‎، و‎T3 (P=7)‎ أقل واحد.
  2. ‎t=0‎: التلاتة وصلوا. T1 الأعلى ⇒ يشتغل [0,1) ويخلص.
  3. ‎t=1..3‎: T2 ⇒ [1,3) ويخلص.
  4. ‎t=3‎: T3 ياخد وحدة واحدة [3,4) — باقيله وحدة.
  5. ‎t=4‎: job جديد من T1 وصل وأولويته أعلى ⇒ يعمل preempt لـ T3 ويشتغل [4,5).
  6. ‎t=5‎: job جديد من T2 وصل وأولويته أعلى من T3 ⇒ T2 يشتغل [5,7).
  7. ‎t=7‎: الـ deadline بتاع T3 جه وهو لسه باقيله وحدة ⇒ Deadline Miss! ✓.

النتيجة: RM فشل رغم إن ‎U = 0.936 < 1‎. ليه؟ لأن شرط الضمان لـ RM (Liu & Layland 1973) هو U ≤ n(21/n − 1) = لـ 3 tasks: 3(21/3−1) = 0.780. إحنا فوقه ⇒ مفيش ضمان (والمحاكاة أثبتت الفشل).

🟡 متوسط ✍️ مثال: EDF خطوة بخطوة
  1. الأولوية هنا بتتغير كل لحظة: اللي الـ deadline بتاعه أقرب هو الأعلى.
  2. ‎t=0‎: deadlines: T1→4، T2→5، T3→7 ⇒ T1 [0,1)، بعده T2 [1,3)، بعده T3 يبدأ عند 3.
  3. ‎t=4‎: T1 وصل بـ deadline 8، لكن T3 الـ deadline بتاعه 7 أقرب ⇒ T3 يكمّل [3,5) ويخلص قبل 7 ✓ (هنا الفرق عن RM!).
  4. ‎t=5‎: T1 (dl 8) و T2 الجديد (dl 10) ⇒ T1 [5,6)، بعده T2 [6,8).
  5. ‎t=8‎: T1 (dl 12)، T3 اللي وصل عند 7 (dl 14) ⇒ T1 [8,9)، بعده T3 [9,11).
  6. ‎t=11‎: T2 (dl 15) [11,13)، ‎t=13‎: T1 (dl 16) [13,14). كله اتلحق.

الـ timeline اللي طلع من المحاكاة: 122331221332213. شرط EDF أبسط بكتير: U ≤ 1 ⇔ كل الـ deadlines تتلحق (لـ tasks مستقلة preemptive بـ ‎deadline = period‎). ده معنى «‎optimal‎»: لو أي خوارزمية تقدر تجدول المجموعة، EDF يقدر.

  1. 🟢 Tasks: ‎T1(C=1,P=3)‎، ‎T2(C=1,P=4)‎. احسب U، وهل RM مضمون؟
    شوف الحل بالتفصيل
    ‎U = 1/3 + 1/4 = 0.583‎. الـ bound لـ ‎n=2‎: 2(√2 − 1) = 0.828. U ≤ bound ⇒ RM مضمون يلحق كل الـ deadlines (ومن باب أولى EDF).
  2. 🟡 T1(2,5)، T2(4,7). اعمل جدول RM لحد ‎t=7‎. فيه miss؟
    شوف الحل بالتفصيل

  3. 🔴 ليه الـ AUTOSAR OS بيستخدم fixed priority (RM-style) مش EDF رغم إن EDF «أحسن»؟
    شوف الحل بالتفصيل

1.6Memory Management — كل process فاكر إنه لوحده

المشكلة: 50 process عايزين يعيشوا في نفس الـ RAM، ومحدش يبوّظ ذاكرة التاني. الحل في Linux اسمه Virtual Memory: كل process بيشتغل بعناوين وهمية (virtual addresses)، وفيه hardware جوه الـ CPU اسمه MMU (Memory Management Unit) بيترجم كل عنوان وهمي لعنوان حقيقي (physical) باستخدام جداول (page tables) الـ kernel بيملاها. الذاكرة بتتقسم لصفحات (pages) غالباً 4 KB.

  • Keeping track: الـ kernel عارف كل page حقيقية مع مين (أو فاضية).
  • Deciding … move into and out of memory: لو الـ RAM خلصت، ممكن ينقل pages مش مستخدمة للـ disk (swap)، أو يرمي pages الكود (لأنها موجودة في الملف أصلاً ويقدر يقراها تاني) — ده اسمه demand paging: البرنامج مبيتحمّلش كله في الأول؛ كل page بتتحمّل أول ما تتلمس.
  • Allocating/deallocating: malloc() في الـ user space بتطلب من الـ kernel بالـ system calls brk()/mmap()، ولما الـ process يموت كل صفحاته ترجع.

1.7File System Management

الـ SD card في الحقيقة مجرد مصفوفة blocks مترقّمة (512 bytes أو 4 KB). الـ filesystem (زي ext4، FAT32، squashfs) هو الـ «‎data structure‎» على الـ disk اللي بتقول الملف الفلاني اسمه إيه وفين blocks بتاعته. في Linux كل ملف ليه inode: رقم + metadata (الحجم، المالك، الصلاحيات، التواريخ، أماكن الـ blocks) — الاسم مش جوه الـ inode؛ الاسم موجود في الـ directory اللي هي ببساطة جدول «اسم ⇐ رقم inode» (هنشوف ده بعينينا مع mv و ls -i في Module 3).

فوق كل الـ filesystems فيه طبقة اسمها VFS (Virtual File System): واجهة موحّدة (open/read/write/close) فبرنامجك يقرا من ext4 أو FAT أو USB أو حتى network بنفس الكود. وفيه filesystems وهمية مالهاش disk أصلاً: /proc و /sys (الـ kernel بيولّد محتواها لحظياً) و tmpfs (في الـ RAM). ومن هنا المبدأ الشهير: «‎Everything is a file‎».

1.8Devices Management — الـ drivers و /dev

الكود اللي بيكلّم الـ hardware الحقيقي اسمه device driver، وبيشتغل جوه الـ kernel (لأنه محتاج يلمس registers ويستقبل interrupts). الـ driver بيعرض الجهاز للـ user space بتلات أشكال:

  • Character device: stream من الـ bytes (UART /dev/ttyS0، I2C /dev/i2c-1، /dev/null).
  • Block device: blocks بـ random access (/dev/mmcblk0 = الـ SD card، /dev/sda).
  • Network interface: مش ملف في /dev؛ اسمه eth0/wlan0 وتكلّمه بالـ sockets.

1.9User Management

الـ kernel مبيعرفش «أسماء» — بيعرف أرقام: كل process شايل UID و GID. الـ root هو UID 0، وأي فحص صلاحيات في الـ kernel بيتعدّى أوتوماتيك لو ‎UID = 0‎. الأسماء (mohamed) مجرد mapping في /etc/passwd (Module 9). وكل ملف شايل ‎UID/GID‎ للمالك + bits الصلاحيات (Module 10). حتى على البورد اللي مفيهاش غير «مستخدم واحد»، الـ services بتشتغل بـ users مختلفة عشان لو واحدة اتخرقت متبوّظش الباقي (principle of least privilege).

1.10Power Management

Sleep modes: لما مفيش process جاهز، الـ scheduler بيشغّل الـ idle task اللي بتنفّذ WFI (Wait For Interrupt) في ARM — الـ core ينام لحد أول interrupt (بالظبط زي SLEEP في الـ PIC). وفيه system-wide suspend (systemctl suspend) = suspend-to-RAM. Clock rate: الـ cpufreq subsystem بيعمل DVFS (Dynamic Voltage & Frequency Scaling): لو الحمل قليل يقلّل الـ clock والـ voltage (القدرة ∝ C·V²·f ⇒ تقليل V بيوفّر كتير). السياسة اسمها governor: performance (أعلى تردد دايماً)، powersave، ondemand/schedutil (حسب الحمل). على البورد: cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor.

📝 📝 Mini-quiz — Module 1
  1. إيه الفرق بين الـ OS والـ kernel؟
    شوف الإجابة
    الـ kernel = قلب الـ OS اللي شغال في الـ privileged mode وبيدير الـ hardware (الست وظايف). الـ ‎OS = kernel + system libraries + shell + utilities‎. «‎Linux‎» = kernel؛ ‎Ubuntu = distribution‎.
  2. برنامج user space عايز يقرا ملف. بيمر بإيه؟
    شوف الإجابة
    fopen/fread في الـ libc ⇒ system call openat/read (trap لـ kernel mode) ⇒ VFS ⇒ driver الـ filesystem ‎(ext4)‎ ⇒ block driver ‎(mmc)‎ ⇒ الـ hardware ⇒ الـ data ترجع بنفس الطريق.
  3. process حالته S في ps. ده معناه إنه بياكل CPU؟
    شوف الإجابة
    لأ. ‎S = sleeping‎: مستني event (timer، ‎I/O‎، input) ومش في الـ run queue أصلاً.
  4. ليه ‎U = 0.936‎ ومع ذلك RM فشل؟
    شوف الإجابة
    لأن شرط RM الكافي ‎U ≤ 0.780‎ لـ 3 tasks؛ فوقه مفيش ضمان، والمحاكاة أثبتت miss لـ T3 عند ‎t=7. EDF‎ نجح لأن شرطه ‎U ≤ 1‎.
  5. ليه الـ boot بيعدّي على SPL قبل U-Boot؟
    شوف الإجابة
    لأن الـ ROM code بيحمّل في الـ SRAM الداخلية الصغيرة، والـ U-Boot الكامل مش هيكفي فيها؛ الـ SPL صغير وشغلته الأساسية يعمل init للـ DDR وبعدين يحمّل U-Boot فيها.
  6. ليه Cortex-M3 مبيشغّلش Linux عادي؟
    شوف الإجابة
    مفيهوش MMU (عنده MPU بس) والذاكرة صغيرة؛ Linux العادي معتمد على الـ virtual memory.
🎤 أسئلة Interview / امتحان
  1. What happens when you power on an embedded Linux board? (السؤال الأشهر)
    الإجابة النموذجية
    ROM code (في الـ SoC) يقرا الـ boot pins ويحمّل SPL للـ SRAM ⇒ SPL يعمل init للـ DDR ويحمّل U-Boot ⇒ U-Boot يحمّل الـ ‎kernel image + DTB (+initramfs)‎ للـ RAM ويبعت bootargs ⇒ الـ kernel يفك نفسه، يفعّل الـ MMU، يقرا الـ DTB، يعمل probe للـ drivers، يعمل mount للـ rootfs ⇒ يشغّل /sbin/init (PID 1) ⇒ services ⇒ getty/login ⇒ shell.
  2. What is a system call? Give an example.
    الإجابة النموذجية
    الواجهة الوحيدة بين الـ user space والـ kernel: instruction (svc/syscall) بتعمل trap لـ privileged mode لـ handler محدد برقم. مثال: write(1, buf, n) اللي printf بتستخدمها؛ نقدر نشوفها بـ strace.
  3. Process vs thread?
    الإجابة النموذجية
    الـ process ليه address space خاص؛ الـ threads جوه نفس الـ process بيشاركوا الـ memory والـ files لكن لكل واحد stack و registers. الـ context switch بين threads أرخص. في Linux الاتنين tasks بتتعمل بـ clone().
  4. RM vs EDF — which is optimal and why is RM still used?
    الإجابة النموذجية
    EDF optimal بين الـ ‎dynamic-priority (U ≤ 1)‎، RM optimal بين الـ fixed-priority (bound 69–78%). RM أبسط، overhead أقل، سلوك متوقّع في الـ overload، وأدوات تحليل ناضجة ⇒ مستخدم في ‎OSEK/AUTOSAR‎.
  5. Why does Linux need an MMU?
    الإجابة النموذجية
    عشان الـ virtual memory: عزل الـ processes، الحماية (الكود read-only، الـ kernel ممنوع)، الـ demand paging، الـ shared libraries، والـ fork بـ copy-on-write.

أي نظام Embedded Linux (من راوتر الـ Wi-Fi لحد شاشة العربية) مبني من 4 مكونات بالظبط، وأدوات البناء (Buildroot/Yocto) بتبنيهم كلهم من الـ source:

S.1الـ Toolchain والـ Cross-compilation

الـ toolchain = مجموعة أدوات بتحوّل الـ C لـ binary: gcc (compiler)، binutils (as assembler، ld linker، objcopy، objdump، readelf)، C library (glibc أو musl أو uClibc-ng) + kernel headers، و gdb. الجهاز اللي بتبني عليه اسمه host (لابتوبك x86_64) والجهاز اللي هيشغّل البرنامج اسمه target (البورد ARM). لما الاتنين مختلفين ⇒ cross-compilation.

S.2الـ Bootloader: U-Boot

شفنا مراحله في الـ boot stepper. U-Boot عنده console على الـ serial (115200 baud) — لو دوست أي زرار في أول ثانيتين بيقف ويدّيك prompt. ده مثال للأوامر اللي هتستخدمها (مش متشغّل في الـ lab بتاعتي لأنه محتاج بورد حقيقية):

U-Boot console (مثال توضيحي)
=> printenv bootcmd                      # الأمر اللي بيتنفذ أوتوماتيك
=> fatls mmc 0:1                         # اعرض ملفات الـ boot partition
=> fatload mmc 0:1 ${kernel_addr_r} Image          # حمّل الـ kernel للـ RAM
=> fatload mmc 0:1 ${fdt_addr_r} bcm2711-rpi-4-b.dtb  # حمّل الـ device tree
=> setenv bootargs console=ttyS0,115200 root=/dev/mmcblk0p2 rootwait
=> booti ${kernel_addr_r} - ${fdt_addr_r}          # ابدأ الـ kernel (ARM64)

S.3الـ Kernel والـ Device Tree

الـ kernel بيتبني من الـ source (kernel.org أو fork الـ vendor). الخطوات: تختار config جاهز للـ SoC، تعدّل فيه، وتبني بالـ cross compiler:

بناء الـ kernel (مثال)
export ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu-
make bcm2711_defconfig        # config جاهز للـ Raspberry Pi 4
make menuconfig               # واجهة تفعّل/تلغي features و drivers
make -j$(nproc) Image modules dtbs
# الناتج: arch/arm64/boot/Image  +  *.ko (modules)  +  *.dtb

الـ Device Tree: زمان كل بورد كان ليها ملف C جوه الـ kernel فيه عناوين الـ peripherals (hard-coded). دلوقتي الوصف ده في ملف نصي .dts بيتعمله compile لـ .dtb والـ bootloader يبعته للـ kernel. نفس الـ kernel image يشتغل على بوردات كتير — بس الـ DTB مختلف. مثال (LED على GPIO + حساس I2C):

board.dts (مثال)
/ {
    leds {
        compatible = "gpio-leds";          /* أنهي driver يمسك الـ node ده */
        status_led: led-0 {
            label = "status";
            gpios = <&gpio 17 GPIO_ACTIVE_HIGH>;   /* GPIO17 */
            linux,default-trigger = "heartbeat";
        };
    };
};
&i2c1 {
    status = "okay";
    clock-frequency = <100000>;
    temp@48 {                               /* عنوان الـ I2C = 0x48 */
        compatible = "ti,tmp102";           /* الـ kernel يدوّر على driver بالاسم ده */
        reg = <0x48>;
    };
};
🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
الـ Device Tree هو أقرب حاجة لـ الـ AUTOSAR configuration ‎(ARXML/ECUC)‎ أو الـ #pragma config + ملف الـ pin mapping في الـ PIC: وصف للـ hardware منفصل عن الكود. الـ driver مكتوب generic («أنا driver الـ tmp102») والـ DT بيقوله «فيه واحد على i2c1 عنوانه 0x48». الكلمة السحرية compatible هي اللي بتربط الـ node بالـ driver (الـ kernel بيعمل match ويشغّل دالة الـ probe() بتاعة الـ driver).

S.4الـ Root filesystem و BusyBox

الـ kernel لوحده مبيعملش حاجة مفيدة — آخر خطوة له إنه يشغّل /sbin/init من الـ rootfs: شجرة الفولدرات اللي هنشرحها في Module 2 (/bin /etc /lib /dev …) فيها الـ init والـ shell والـ libc والبرامج. في الـ embedded بنستخدم BusyBox: binary واحد (~1 MB) فيه نسخ مصغّرة من 300+ أمر (ls, cp, grep, vi, sh, init …)؛ و/bin/ls مجرد symlink ليه — BusyBox بيبص على اسمه اللي اتنادى بيه (argv[0]) ويشتغل على أساسه. كل الأوامر اللي في Modules 2–11 هتلاقيها على البورد بالشكل ده (مع اختلافات بسيطة في الـ options).

2.2يعني إيه Terminal و Shell؟ وصيغة الأوامر

Terminal (أو terminal emulator) = الشباك اللي بيعرض نص ويستقبل كيبورد (GNOME Terminal). Shell = البرنامج اللي جواه بيقرا الأوامر وينفّذها — الافتراضي bash (Bourne Again SHell). الـ shell مجرد برنامج user space عادي؛ ينفع تغيّره (zsh، sh، BusyBox ash).

صيغة أي أمر: command [options] [arguments] — الأقواس المربعة [ ] في الـ documentation معناها اختياري. الـ options بتغيّر سلوك الأمر وبتبدأ بـ - (short: -l) أو -- (long: --all). الـ arguments = الحاجات اللي الأمر هيشتغل عليها (ملفات، فولدرات). والـ ; بتفصل أوامر على نفس السطر: pwd; whoami; uname = اتنفذوا ورا بعض (حتى لو واحد فشل — بعكس && في Module 5).

🔬 إيه اللي بيحصل بالظبط لما تكتب ls -l Documents وتدوس Enter؟
  1. read: الـ shell بتقرا السطر.
  2. parse: تقسّمه لكلمات بالمسافات (ده سبب إن المسافة في اسم الملف مشكلة!) وتتعرف على الـ operators (; | && >).
  3. expand: تبدّل ~ و $VAR و $(…) و {1..3} و * — قبل ما الأمر يشتغل (Modules 4–6).
  4. redirect: تجهّز الـ > file (Module 5).
  5. find: الكلمة الأولى builtin (جوه الـ shell)؟ ولا برنامج؟ لو برنامج تدوّر عليه في الفولدرات اللي في $PATH بالترتيب.
  6. fork(): الـ shell تعمل نسخة من نفسها (child process).
  7. exec(): الـ child يستبدل نفسه بالبرنامج /usr/bin/ls ويديله الـ arguments: argv = ["ls", "-l", "Documents"] — بالظبط الـ int main(int argc, char *argv[]) اللي تعرفها في C!
  8. wait(): الأب (الـ shell) يستنى الـ child يخلص ويحفظ الـ exit status في $? ويطبع الـ prompt تاني.

2.8قواعد أسماء الملفات

  • Any characters: فعلاً، الـ kernel بيمنع حرفين بس: / (الفاصل) و \0 ‎(NUL)‎. أقصى طول للاسم 255 byte. بس ? * [ ] > < | ; & $ # ' " \ ليها معنى عند الـ shell (wildcards، redirection، comments) فهتتعب وإنت بتكتبها.
  • No extensions: الـ kernel مبيبصش على .txt — الملف التنفيذي بيتعرف بالـ x permission وبالـ «‎magic number‎» في أوله (ELF بيبدأ بـ \x7fELF)؛ الأمر file بيقرا الـ magic. بس بعض البرامج بتهتم بالامتداد (gcc بيفرّق بين .c و .cpp، و make، والـ GUI).
  • Case sensitive: File1 و file1 و FILE1 تلات ملفات مختلفة (عكس Windows). وده بينطبق على الأوامر كمان: LS ≠ ls.
  • Hidden: أي اسم يبدأ بـ . (مثلاً .bashrc ملف إعدادات الـ bash) — مجرد اتفاق: ls والـ * بيتجاهلوه، مش حماية.
  • Spaces: استخدم my_file أو my-file. لو لازم مسافة: "my file" أو my\ file.
⚠️ خلي بالك
اسم يبدأ بـ - (زي -rf) خطير: rm -rf هيتفهم option! لو اتعمل بالغلط امسحه بـ rm -- -rf (الـ -- = خلصت الـ options) أو rm ./-rf.

3.1cp — نسخ

القاعدة الذهبية: آخر argument هو الـ destination، وكل اللي قبله sources. لو فيه أكتر من source، الـ destination لازم يكون directory موجود. لو source واحد والـ destination مش موجود ⇒ نسخة جديدة بالاسم ده. لو الـ destination ملف موجود ⇒ بيتكتب فوقه بصمت (مفيش سؤال!) — علشان كده -i (interactive) بيسأل الأول.

4.1يعني إيه Wild card؟

أهم سر في الوحدة دي: الـ shell هي اللي بتفك الـ wildcard، مش الأمر. لما تكتب rm *.txt، الـ bash (في خطوة الـ expand اللي في رسمة Module 2) بتبص في الفولدر، تلاقي notes.txt report.txt، وتبدّل النمط بيهم، وبعدين تشغّل rm notes.txt report.txt. الـ rm عمره ما شاف نجمة! الاسم الرسمي للعملية دي globbing أو pathname expansion. وعشان نشوف «الأمر الحقيقي» بنستخدم echo بدل الأمر — echo بيطبع الـ arguments اللي وصلته.

🤔 ليه كده؟
ليه التصميم ده؟ عشان كل الأوامر (ls, cp, rm, gcc, …) تستفيد من الـ wildcards من غير ما كل واحد يكتب كود globbing لنفسه. نتيجة جانبية مهمة: الأمر مبيعرفش إنك كتبت نجمة، ولو مفيش matches بيحصل سلوك غريب (شوف تحت).

4.3الأقواس المربعة: [abc] و [!abc] و [a-z] و [[:class:]]

القوسين المربعين = حرف واحد بس من مجموعة. جوّاهم: قايمة ([afe])، أو range ([a-e])، أو خليط ([1-47-9] = range 1–‎4 + range 7‎–9، مش «47»!)، أو class ([[:digit:]] — لاحظ القوسين: الخارجي هو الـ bracket والداخلي [:digit:] اسم الـ class). و ! في الأول = نفي (bash بيقبل ^ كمان).

4.4الأقواس المعقوفة { } — Brace expansion

💡 ملاحظة دقيقة
الـ { } تقنياً مش wildcard: اسمها brace expansion وبتحصل قبل الـ globbing ومن غير ما تبص على الملفات الموجودة خالص — مجرد توليد نصوص. علشان كده mkdir folder{1,2,3} بيشتغل رغم إن الفولدرات مش موجودة (الـ wildcard عمره ما يعمل حاجة مش موجودة). في rm {*.txt,*.doc} اللي بيحصل: braces ⇒ rm *.txt *.doc ⇒ وبعدين globbing لكل واحد. لو مفيش ولا ملف .doc، الـ *.doc هيوصل حرفي و rm هيقول cannot remove '*.doc' (بس هيمسح الـ .txt عادي).

5.8الـ Exit status و && و ||

كل أمر لما يخلص بيرجّع رقم اسمه exit status (الـ return بتاع main() أو exit(n)): 0 = نجاح، وأي رقم تاني (1–255) = فشل (والرقم بيوضّح نوع الفشل). الـ shell بتحفظه في $?. خلي بالك: ده عكس الـ C — في C الصفر false، هنا الصفر = نجاح = «‎true‎».

mohamed@embedded-pc:~/lab$ mkdir folder1 || ls

folder1
mohamed@embedded-pc:~/lab$ cat file1 || echo "File not exist"

File not exist

mohamed@embedded-pc:~/lab$ mkdir -p build && cd build && pwd

🔍 السطور دي معناها إيه؟ — سطر بسطر
mkdir folder1 && ls ⇒ folder1
نجح ⇒ الـ ls اتنفذ.
(المرة التانية) File exists — ومفيش ls
فشل (موجود) ⇒ الـ && وقفت.
mkdir folder1 || ls ⇒ error ثم folder1
فشل ⇒ الـ || نفّذت الـ ls.
cat … || echo "File not exist"
error handling: الـ cat فشل فطبعنا رسالتنا.
exit status = 2
ls بترجّع 2 للـ «‎serious trouble‎» (ملف مش موجود)، و1 للمشاكل البسيطة. كل أمر بيوثّق أرقامه في الـ man (EXIT STATUS).

أوامر وظيفتها بس ترجّع الرقم ده.

🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
ده نفس الـ short-circuit evaluation في C: if (init() && start()) — start مش هتتنادى لو init فشلت. والـ AUTOSAR بيرجّع Std_ReturnType ‎(E_OK = 0 / E_NOT_OK = 1)‎ — نفس الاتفاقية: صفر = تمام.
🪤 فخ امتحانات
cmd1 && cmd2 || cmd3 مش if/else بالظبط: لو cmd1 نجح و cmd2 فشل، cmd3 هتتنفذ كمان! للـ if/else الحقيقي استخدم if cmd1; then cmd2; else cmd3; fi.

💡 تدقيق: الـ load average مش «‎CPU load‎» بالظبط

6.4الـ Pipes |

اللي بيحصل حرفياً في cat file1 | grep linux:

  1. الـ shell بتنادي pipe(fds) ⇒ الـ kernel بيعمل buffer في الذاكرة (64KB افتراضياً) وبيرجّع 2 fd: طرف كتابة وطرف قراية.
  2. fork() مرتين ⇒ process لـ cat و process لـ grep — الاتنين شغالين في نفس الوقت (مش واحد ورا التاني).
  3. في process الـ cat: dup2(write_end, 1) ⇒ الـ stdout بقى الـ pipe. في الـ grep: dup2(read_end, 0).
  4. cat بيكتب؛ لو الـ buffer اتملى الـ kernel بينيّمه (block) لحد ما grep يقرا. grep لو الـ buffer فاضي بينام لحد ما ييجي data — ده flow control أوتوماتيك.
  5. cat يخلص ويقفل ⇒ grep بيقرا EOF ⇒ يخلص. الـ shell تستنى الاتنين.
🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
الـ pipe = ring buffer بين task producer و task consumer بالظبط زي Queue في FreeRTOS: xQueueSend بيـ block لو مليانة، و xQueueReceive بيـ block لو فاضية. أو زي الـ UART RX FIFO بين الـ ISR والـ main loop. الفرق إن الـ kernel هو اللي بيدير كل ده.

9.3/etc/shadow حقل حقل

قيمة الحقل التانيالمعنى
$y$…hash بـ yescrypt (الافتراضي في Ubuntu الحديث). $6$ = SHA-512، $1$ = MD5 (قديم). الشكل: $id$salt$hash
! أو !$y$…مقفول (locked) — الـ ! قدام الـ hash بتخليه ميطابقش أي password
*مفيش password خالص (system accounts)
فاضيpasswordless (خطر!)
⚠️ خلي بالك — غلطة شائعة
ناس كتير بتكتب «encrypted password». الأدق: hashed. الـ encryption بيترجع بمفتاح، لكن الـ hash دالة اتجاه واحد: النظام عمره ما بيفك الـ password — لما تكتب password وقت الـ login، بيحسب الـ hash بنفس الـ salt ويقارن. ده سؤال انترفيو مشهور. وكمان «‎readable only by root‎»: على Ubuntu الملف -rw-r----- root shadow يعني group shadow كمان بتقراه (برامج زي unix_chkpwd).
🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
الـ ‎salt + hash‎ ده نفس فكرة الـ secure boot على الـ MCU: البوت لودر مش بيخزن الـ firmware «السري»، بيخزن hash/توقيع ويقارن. ولو بتعمل نظام login على جهاز embedded (web UI مثلاً) اعمل نفس الحكاية: متخزنش passwords أبداً، خزّن salted hash.

10.1الملكية: owner و group

كل ملف في الـ inode بتاعه (Module 2) متخزّن: UID صاحبه، GID الجروب، وmode = 16 bit: 4 لنوع الملف + ‎3 special + 9‎ صلاحيات. ولما process يحاول يفتح ملف الـ kernel بيعمل الفحص ده بالترتيب وبيقف عند أول واحد ينطبق:

  1. لو الـ process بـ UID 0 ‎(root)‎ ⇒ مسموح تقريباً كل حاجة (القراءة/الكتابة دايماً؛ التنفيذ لو أي x موجودة).
  2. لو UID الـ ‎process = UID‎ الملف ⇒ استخدم bits الـ owner بس — وخلاص.
  3. وإلا لو GID الـ process أو أي ‎supplementary group = GID‎ الملف ⇒ استخدم bits الـ group.
  4. وإلا ⇒ bits الـ others.
🪤 فخ امتحانات
بسبب «أول واحد ينطبق»: ملف ----rwxrwx صاحبه mohamed ⇒ mohamed نفسه ممنوع يقراه رغم إن الـ group والـ others مسموح لهم! (بس هو صاحبه فيقدر يعمل chmod يرجّع الصلاحيات.)

ده الإثبات: لو كان طرح كان الملف هيبقى 633 (-rw--wx-wx). الحقيقي 666 & ~033: الـ ‎3 = -wx‎ ⇒ شيل w و x من group و ‎others ⇒ rw-r--r-- = 644‎.

خاص جداً — مناسب لـ root أو لملفات سرية.

⚠️ خلي بالك — غلطة شائعة
ناس كتير بتكتب الـ umask «value that is subtracted» و 666 - 022 = 644. النتيجة صح بالصدفة بس الطريقة غلط: الـ kernel بيعمل AND NOT مش طرح: mode = 0666 & ~umask. الفرق يبان لما الـ umask فيه bits مش موجودة في الافتراضي: umask 033 ⇒ بالطرح ‎666−033‎ = 633 (rw--wx-wx — مستحيل يدّي x لملف!) والحقيقي 644 (جرّبته فوق). القاعدة: الـ umask بيـشيل bits، عمره ما بيضيف. (وكمان الملفات مبتاخدش x من الـ umask أبداً لأن الافتراضي 666 — عشان كده لازم chmod +x.)
🔌 قارن بعالم الـ MCU اللي إنت عارفه ‎(PIC / AUTOSAR)‎
mode = requested & ~umask = نفس الـ interrupt mask: الـ IE bits ماسك بيمنع، والمطلوب بيعدي بس لو مش مقفول. وفي C: open("f", O_CREAT|O_WRONLY, 0666) ⇒ الـ kernel بيطبق الماسك بنفسه، و umask(022) system call بيغيره للـ process.

    شوف الحل بالتفصيل

شائع: find . -type d -exec chmod -R 755 {} \; — الـ -R هنا غلط عملياً: أول directory يلاقيه find هو . نفسه ⇒ chmod -R 755 . هيدّي كل الملفات (مش الفولدرات بس) صلاحية x، وبعدين يعيد نفس الشغل على كل فولدر فرعي تاني (شغل مكرر). المقصود «الفولدرات بس 755» يتكتب: find . -type d -exec chmod 755 {} + (ومعاه للملفات find . -type f -exec chmod 644 {} +). وكمان find ~ -type f -empty -exec rm {} \; على الـ home كله خطر: فيه ملفات فاضية مقصودة (lock files، markers زي .sudo_as_admin_successful) — جرّب بـ -print الأول.

Glossary — قاموس المصطلحات

كل مصطلح بجملة أو اتنين
Kernel
قلب الـ OS: بيدير الـ CPU (scheduler) والذاكرة ‎(MMU)‎ والأجهزة (drivers) والملفات، وشغال في kernel space بصلاحيات كاملة.
User space / Kernel space
منطقتين معزولين بالـ hardware (EL0/EL1 في ARM)؛ البرامج العادية مبتلمسش الـ hardware إلا عن طريق system calls.
System call
الباب الرسمي من user space للـ kernel (open, read, write, fork, execve…) — بيتم بـ instruction خاصة (svc / syscall).
Bootloader (U-Boot)
بيهيّأ الـ DRAM والـ clocks ويحمّل الـ kernel والـ DTB في الذاكرة ويقفز له.
Device Tree ‎(DTB)‎
وصف للـ hardware (عناوين، interrupts، pins) بيقراه الـ kernel بدل ما يتكتب في الكود.
init (PID 1)
أول process في user space (systemd أو BusyBox init)؛ بيشغّل كل الباقي.
RootFS
الـ filesystem اللي فيه /bin /etc /lib … اللي الـ kernel بيعمله mount كـ /.
Toolchain / Cross-compiler
‎gcc + binutils + C library‎ مبنيين يطلعوا كود لـ architecture تانية (aarch64-linux-gnu-gcc).
Buildroot / Yocto
أدوات بتبني ‎toolchain + kernel + bootloader + rootfs‎ من الـ source.
BusyBox
binary واحد فيه نسخ مصغّرة من مئات الأوامر — شائع جداً في الـ embedded rootfs.
Process
برنامج شغال: ذاكرة خاصة ‎(virtual address space) + PID + fds + UID/GID‎.
fork / exec
fork = نسخ الـ process؛ exec = استبدال البرنامج جوه الـ process. كل أمر في الـ ‎shell = fork+exec‎.
Scheduler / RM / EDF
اللي بيقرر مين ياخد الـ CPU؛ RM = أولوية ثابتة بالـ period؛ EDF = أقرب deadline.
MMU / Virtual memory
كل process شايف عناوين وهمية والـ MMU بيترجمها لعناوين حقيقية بالـ page tables — عزل وحماية.
FHS
المعيار اللي بيحدد معنى كل فولدر (/etc configs، /dev أجهزة، /proc معلومات الـ kernel…).
Inode
الـ struct اللي فيه كل معلومات الملف (owner, mode, size, block pointers) ماعدا الاسم.
Directory
ملف خاص فيه جدول «اسم ⇐ رقم inode».
Absolute / Relative path
من / / من الفولدر الحالي.
Shell
برنامج بيقرا الأوامر، يفكّها (expansions)، ويعمل ‎fork+exec‎.
Builtin
أمر جوه الـ shell نفسها (cd, echo, pushd) — مش ملف.
PATH
قايمة الفولدرات اللي الـ shell بتدوّر فيها على الأوامر.
Globbing / Wildcards
الـ shell بتفك * ? [ ] لأسماء ملفات موجودة.
Brace expansion
{a,b} {1..5} — توليد نصوص بغض النظر عن الملفات.
Exit status
رقم 0–255 بيرجّعه الأمر؛ 0 = نجاح؛ في $?.
File descriptor
رقم بيمثل ملف مفتوح في process: 0 stdin، 1 stdout، 2 stderr.
Redirection
تغيير fd لملف قبل الـ exec (> >> 2> < 2>&1).
/dev/null
جهاز بيرمي أي كتابة.
Pipe
buffer في الـ kernel بيوصّل stdout process بـ stdin process تاني.
Command substitution
$‎(cmd)‎ — حط الـ output مكانه.
Quoting
' ' حرفي، " " بيفك $، \ بيهرب حرف.
Regex (BRE / ERE)
لغة لوصف أنماط النص؛ ERE فيها + ? | {} () كـ meta مباشرة.
Anchor
^ بداية السطر، $ نهايته.
Character class
[[:digit:]] [[:alpha:]] …
Modal editor
vim: Normal / Insert / Command-line / Visual.
‎UID / GID‎
الأرقام اللي الـ kernel بيعرف بيها المستخدمين والجروبات؛ ‎UID 0 = root‎.
/etc/passwd · /etc/shadow · /etc/group
databases المستخدمين / الـ hashes والـ aging / الجروبات.
‎Hash + salt‎
تخزين الـ password كبصمة اتجاه واحد مع salt عشوائي.
Primary / Supplementary group
الجروب الأساسي (GID في passwd) / الإضافية (في /etc/group).
Permission bits
‎r=4 w=2 x=1‎ لـ owner/group/others.
SUID / SGID / Sticky
4000 تشغيل بصلاحيات الـ owner / 2000 جروب الملف أو وراثة جروب الفولدر / 1000 حماية المسح في الفولدر المشترك.
Effective UID
الـ UID اللي بيتفحص بيه الصلاحيات (بيتغير مع SUID).
umask
ماسك بيشيل bits من ‎666/777‎ للملفات الجديدة: mode & ~umask.
Login shell
shell بتقرا ملفات الـ login (.profile) — su - / ssh.
find expression
‎tests + operators (-a -o !) + actions (-print -exec -delete)‎، من الشمال لليمين.
locate / updatedb
بحث في database أسماء جاهزة / تحديثها.
Load average
متوسط عدد الـ tasks في حالة R أو D على ‎1/5/15‎ دقيقة.

وصفة لكل نوع سؤال في الامتحان أو الـ ‎interview + quiz‎ نهائي

🧭 عرّف / What is X?

جملة تعريف (إيه هو) ⇐ ليه موجود (المشكلة اللي بيحلها) ⇐ إزاي بيشتغل من جوه (سطر أو اتنين) ⇐ مثال/أمر ⇐ مقارنة سريعة بحاجة قريبة. مثال: «umask = ماسك للصلاحيات الافتراضية… ‎mode = 666‎ & ~umask… مثال 022 ⇒ 644».

🧭 قارن / Difference between A and B

جدول أو نقاط على نفس المحاور: الوظيفة، إزاي بيشتغل، السرعة، الصلاحيات، امتى تستخدم ده وامتى ده. (find/locate، su/sudo، ‎BRE/ERE‎، > و >>، hard/soft، -G و -aG، \; و +).

🧭 اتوقع الـ output

نفّذ في دماغك زي الـ shell بالترتيب: 1) brace 2) $var و $‎(cmd)‎ 3) word splitting 4) globbing على الملفات الموجودة 5) الـ redirections من الشمال لليمين 6) الأمر نفسه. وخلي بالك من: no-match يفضل حرفي، hidden files، الترتيب الأبجدي، ‎2>&1 order‎، grep -c بيعد سطور، sort نصي.

🧭 اكتب الأمر

حدد: المدخل (ملف؟ pipe؟) ⇐ الشرط ⇐ الفعل ⇐ المخرج. ابدأ بالأمر الأساسي وزوّد options. حط الـ patterns بين quotes. اعمل dry-run (echo / -print) قبل أي مسح.

🧭 صلاحيات / احسب

حوّل كل 3 bits لرقم (r4 w2 x1). للـ umask: AND NOT مش طرح. للفولدر افتكر x = دخول و ‎w+x‎ = إنشاء/مسح. حدد الفئة الأول (owner؟ group؟ others؟) — أول واحد ينطبق بس.

🧭 اكتب regex

اكتب أمثلة لازم تطابق وأمثلة لازم متطابقش ⇐ ابني جزء جزء (anchors، classes، quantifiers) ⇐ جرّب في الـ regex tester ⇐ اختار BRE ولا ERE (-E).

🧭 اشرح الـ error / Troubleshoot

اقرا الرسالة حرفياً (مين اللي طلّعها: bash؟ الأمر؟) ⇐ صنّفها: No such file (مسار/glob)، Permission denied (r/w/x أو root)، command not found (PATH/اسم/case)، invalid option ⇐ أثبت بأمر (ls -l، id، type، echo pattern) ⇐ صلّح.

🧭 سيناريو Embedded

اربط بالسلسلة: boot (ROM ⇐ SPL ⇐ U-Boot ⇐ ‎kernel+DTB‎ ⇐ init) أو بالـ rootfs (users، permissions، /dev، /sys) أو بالـ toolchain. اذكر الأداة (Buildroot/Yocto) وإزاي تتأكد (dmesg، uname -a، file app).

🧭 سؤال ‎RM/EDF‎
